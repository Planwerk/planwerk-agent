# Review Pattern: GitHub Actions Workflow Security

**Review-Area**: security
**Detection-Hint**: `${{ github.event.* }}`, `${{ github.head_ref }}` or `${{ inputs.* }}` inside `run:` or a `github-script` `script:`, `pull_request_target`/`workflow_run`/`issue_comment` jobs that check out and run the pull request's code, no `permissions:` key or `write-all`, secrets interpolated into `run:` or set in workflow-level `env:`, `secrets: inherit`, untrusted text written to `$GITHUB_ENV`, pull-request artifacts or caches reaching a privileged job, `runs-on: self-hosted` in a public repository
**Severity**: CRITICAL
**Category**: technology
**Applies-When**: github-actions
**Sources**: GitHub Docs — Security hardening for GitHub Actions: Secure use reference (https://docs.github.com/en/actions/reference/security/secure-use), GitHub Docs — Script injections (https://docs.github.com/en/actions/concepts/security/script-injections), GitHub Docs — Workflow syntax: permissions (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions), GitHub Docs — Dependency caching reference (https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), GitHub Security Lab — Keeping your GitHub Actions and workflows secure Part 1: Preventing pwn requests (https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/), GitHub Security Lab — Keeping your GitHub Actions and workflows secure Part 2: Untrusted input (https://securitylab.github.com/resources/github-actions-untrusted-input/), GitHub Security Lab — Keeping your GitHub Actions and workflows secure Part 4: New vulnerability patterns and mitigation strategies (https://securitylab.github.com/resources/github-actions-new-patterns-and-mitigations/), OpenSSF Scorecard checks: Dangerous-Workflow and Token-Permissions (https://github.com/ossf/scorecard/blob/main/docs/checks.md)

## What to check

This pattern covers `.github/workflows/` and the `run:` steps of composite actions (`action.yml`). Pinning actions by commit SHA is the check of `Software Supply-Chain Integrity`.

### Untrusted input
1. A `${{ }}` expression inside `run:` (or the `script:` of `actions/github-script`) that expands text an outside contributor chooses is script injection: the runner pastes the value into the script before the shell parses it. Such text includes the title and body of an issue, pull request, comment or review, `github.event.pull_request.head.ref` and `head.label`, `github.head_ref`, commit messages and author names and emails, and the `inputs.*` of a composite action or `workflow_call` workflow. The fix passes the value through the step's `env:` and quotes it (`"$TITLE"`)
2. Untrusted text appended to `$GITHUB_ENV`, `$GITHUB_PATH` or `$GITHUB_OUTPUT` reaches every later step: a value that sets `BASH_ENV` or `LD_PRELOAD`, or a multi-line value that forges a `NAME=value` line, runs code in a step that never read it. The step checks the value's shape (a number, a SHA, a known label) first

### Privileged triggers
3. `pull_request_target`, `workflow_run` and `issue_comment` run with the base repository's secrets and a writable `GITHUB_TOKEN`, also for a fork's pull request. A job under one of them that checks out the pull request's code (`github.event.pull_request.head.sha`, `head.ref`, `refs/pull/<n>/merge`, `gh pr checkout`) and then runs any of it (install, build, test, `make`, a local `uses: ./`, a config file a tool loads as code) hands both to the author. The safe shape runs the code in an unprivileged `pull_request` workflow and acts on its result in a privileged one that executes none of it
4. A job gated on a label, approval or comment checks out the approved commit (`head.sha`), not a branch name: a push after the approval changes what the name resolves to
5. An artifact a privileged `workflow_run` job downloads was written by the pull request's code. The job extracts it under `$RUNNER_TEMP`, away from anything a later step executes, and parses it as data
6. A job on a low-trust trigger (`pull_request_target`, `issue_comment`, `workflow_run`) gets read-only access to the default branch's cache; one that declares `cache-mode: write` or `write-only` lets a poisoned entry in, and trusted runs restore it. A release or publishing job builds with caching off (`cache: false` on `actions/setup-*`, no `actions/cache`)

### Token and secret scope
7. A workflow declares `permissions:` at the top as `contents: read` or `{}`, and a job raises only the scopes its own steps use. Without the key a workflow inherits the repository or organization default, which is write access on older repositories and invisible in the diff; `write-all` grants every scope. A personal access token used where `GITHUB_TOKEN` would do widens a leak to every repository its owner can write
8. A job that does not push sets `persist-credentials: false` on `actions/checkout`, so no later step that runs untrusted code can use the token, and no upload of the workspace carries it away from `.git/config`, where checkout before v6 writes it
9. A secret reaches only the step that uses it, through that step's `env:` or an action input. Interpolated into `run:` it lands in the script on disk; in workflow-level `env:` every step and action of every job sees it; masking matches only the exact string, so an encoded or split value prints in clear. `secrets: inherit` passes every secret the caller can read, not only the ones the called workflow uses, and a credential written into the workflow file is readable by anyone who can read the repository

### Runners and references
10. Reusable workflows (`uses: owner/repo/.github/workflows/x.yml@ref`) and `docker://` actions are pinned by commit SHA and image digest, like actions: a moving `@main` on a reusable workflow that receives secrets hands them to whoever can push there
11. A public repository's workflow that a fork contributor can trigger runs on GitHub-hosted or ephemeral just-in-time runners. On a persistent `runs-on: self-hosted` runner, outside contributors run code inside its network, and the next job inherits what the last one left. When the checkout does not show the repository's visibility, report the finding and say it holds for a public repository

## Not a finding

- A `${{ }}` expression in `if:`, `runs-on:`, `strategy.matrix`, `concurrency:`, `env:`, or the `with:` input of an action that takes it as data: the runner substitutes it as a value, not as script text. An input the action runs as code, such as `github-script`'s `script:`, is still a finding under item 1, and a secret in workflow-level `env:` under item 9.
- An expression in `run:` whose value an outside contributor cannot choose: `github.sha`, `github.event.pull_request.number`, `github.event.pull_request.head.sha`, `github.run_id`, `github.repository`, `github.event_name`. The same event's title or branch name is still a finding.
- A `pull_request` workflow that checks out and runs the pull request's code: a fork's run gets no secrets and a read-only token. The same steps under `pull_request_target` are still a finding under item 3.
- A `pull_request_target`, `workflow_run` or `issue_comment` job that labels, comments, triages, checks out only the base branch, or reads the head as data with nothing from it installed, built, executed or loaded as configuration. A step that runs a file from the head makes it a finding.
- Write scopes at the top of a workflow whose every job uses them, and a scope a called reusable workflow documents as required (`slsa-framework/slsa-github-generator` needs `actions: read`, `id-token: write`, `contents: write`). A job that inherits a write scope it does not use is still a finding under item 7.
- An action referenced by tag, which `Software Supply-Chain Integrity` owns, and the `slsa-github-generator` reusable workflows at an `@vX.Y.Z` tag, which their provenance verification requires. Any other reusable workflow at a tag or branch, or a `docker://` action without an `@sha256:` digest, is still a finding under item 10.
- `runs-on: self-hosted` in a private repository, or in a workflow that only `push`, `schedule`, `workflow_dispatch` or `release` triggers. A public repository's workflow that a fork's pull request or a comment can trigger is still a finding under item 11.

## Why it matters

A workflow runs with the repository's credentials whenever its trigger fires, and several triggers fire on events a stranger starts: an issue, a comment, a fork's pull request. GitHub Security Lab's series documents the recurring shapes: the pwn request, script injection through expressions, artifacts and caches that carry a pull request's bytes into a privileged run, and tokens broad enough to turn any of them into a push or a release. In December 2024 the `ultralytics` package on PyPI shipped a cryptominer after a `pull_request_target` workflow expanded an attacker's branch name inside `run:`; published analyses trace the path to the release through the cache the release workflow restored. CI runs these few untested lines of YAML with full trust, so the pull request that adds one is the cheapest place to catch it.
